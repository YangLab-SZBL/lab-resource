4.0 软件形态与两条推荐路线

平台已在 一号集群部署 DIA-NN 2.6.1 的 Singularity 容器镜像（软件升级由平台负责，无需自行安装）。容器＝把软件连同运行环境整体打包（镜像文件以 .sif 结尾，概念见《HPC 使用入门》0.4），不理解机制也没关系，命令里路径照抄即可。唯一要养成的习惯：每个新开的终端窗口，用 DIA-NN 前先执行一次 module load singularity/ce-3.8.0（把容器运行环境“加载”进当前窗口，关掉窗口就失效，下次重开要再执行）：

/lustre/software/diann/2.6.1/diann261.sif     # 容器镜像（可直接执行，等价于 singularity run/exec）
/lustre/software/diann/2.6.1/                   # 目录
# 使用前加载 Singularity 模块（两种路线都需要）
module load singularity/ce-3.8.0

两条路线任选：

路线适用做法
A. sbatch 一键批处理（推荐）正式数据分析，样本多、时间长写 .sh 提交作业 → tail 看日志 → 结束后拷结果（本册 4.1）
B. 交互式前台调试验证参数、单/少样本试跑salloc 上计算节点 → 前台直接跑（小样本）→ 用完 exit（本册 4.2）

4.1 路线 A：sbatch 提交 DIA-NN（正式分析）

DIA-NN 工作流四铁律（组内实战总结，先读再写脚本） ① 建库先行，候选集在建库时定格：漏切数、修饰声明、肽段/质荷比窗口都在“FASTA 虚拟酶切”时决定谱库内容；搜库阶段改这些参数不会改变候选集（纯库搜索不再消化 FASTA，见下方说明框①）。建库用哪个 FASTA 直接影响结果：尽量无 decoy、contaminant 与 isoform 按需取舍（见说明框③）。 ② 搜库时谱库与 fasta 必须匹配：--lib 谱库与 --fasta 注释文件应为同一物种、同一来源版本（如均为人类 UniProt UP000005640），否则报告里的蛋白名/基因注释会错乱或缺失。分析时的 fasta 只做注释，不要再加 --fasta-search（那是建库参数）。 ③ 线程：32 核节点可以申请 64 线程：cu-1 为 32 物理核（超线程 64 逻辑核），--ntasks-per-node=64 + --threads 64 可正常排队运行（组内实测）；但超线程对 DIA-NN 一般无额外加速，32 与 64 哪个快以实测为准（见 4.4③）。 ④ 重搜前清 .quant；MBR 尽量开启：换库/改参数重新搜库同一批 mzML/raw 前，先 rm -f *.quant 删除旧中间缓存（否则旧搜索的识别结果可能被复用，见 4.3 表中 *.quant 行）；--reanalyse（MBR）在预测谱库定量分析中尽量保持开启（官方推荐，见说明框②）。
1
准备数据目录：mkdir ~/diann_test（建议每次分析建独立目录），将 .raw（若用 Bruker 仪器则为整个 .d 文件夹；Linux 容器还支持 .mzML）、已有谱库（如 human.predicted.speclib）上传到同一目录（cd 到该目录再提交作业，避免路径问题）；fasta 建议一并放好，角色是蛋白注释（见下方对照框说明③）。若习惯脚本与数据分目录存放，路径怎么写见下框。
路径提示：脚本与 raw/fasta 不在同一目录怎么办

先记原则：sbatch 作业的“当前目录”＝你执行 sbatch 时所在的目录（Slurm 环境变量 SLURM_SUBMIT_DIR），与 .sh 脚本放在哪里无关；脚本里的相对路径、%j.out/.err 都从该目录解析。所以最省事的做法是“进数据目录提交，脚本放任何位置”：

cd /lustre/你的路径/数据目录
sbatch ~/scripts/diann_job.sh        # 脚本路径写绝对路径（或相对路径）即可

脚本内仍写相对文件名（--f "xxx.raw"），一行都不用改。其余两种等价写法：

① 全部写绝对路径（数据分散在多个目录时最稳）：每个 --f、--fasta、--lib 各自带全路径；--out "/lustre/…/result/report.parquet" 同时决定结果写到哪（所有派生文件跟随它）；想让 %j.out/.err 也进结果目录，另加 #SBATCH --output=/lustre/…/result/%j.out。

② 在脚本里指定工作目录：头部加 #SBATCH --chdir=/lustre/…/数据目录（作业直接在该目录启动），或在主命令前加一行 cd /lustre/…/数据目录。

补充：登录后可用 pwd 查看自己账号的完整路径（一般形如 /lustre/账号名/…）；某目录内 raw 很多时，可改用 --dir "/lustre/…/raw目录" 一次处理整个文件夹（--dir-all 则递归子目录），省去一长串 --f；含空格的路径参数务必用引号包住。

2
编写作业脚本（vim 新建 diann_job.sh；不会 vim 的替代法与保存/退出速记见下方“新手实操”框）。DIA-NN 官方流程分两步：① 从 FASTA 生成预测谱库（一次性）；② 用谱库分析原始数据（每次实验）。已有 human.predicted.speclib 就按下面的“分析模板”写；没有则先按“建库模板”跑一次。分析模板为本组实测可用：
#!/bin/bash
#SBATCH --job-name=diann_search
#SBATCH --partition=cu-1          # 32核队列；如队列忙可加 cu-short,cu-1 让调度器按序尝试
#SBATCH --nodes=1
#SBATCH --ntasks-per-node=32      # 与下方 --threads 保持一致（想试 64 线程：两处同改 64，见 4.4③）
#SBATCH --time=24:00:00
#SBATCH --output=%j.out
#SBATCH --error=%j.err

module load singularity/ce-3.8.0

# 分析模板：镜像文件 + 容器内程序路径 + 参数（写法：镜像 + 容器内 diann-linux + 参数）
/lustre/software/diann/2.6.1/diann261.sif /diann-2.6.1/diann-linux \
  --f "20260730_ky_hela_1ug_dia_1.raw" --f "20260730_ky_hela_1ug_dia_2.raw" \
  --f "20260730_ky_hela_1ug_dia_3.raw" --f "20260730_ky_hela_1ug_dia_4.raw" \
  --lib "human.predicted.speclib" \
  --fasta "2026-07-14-decoys-reviewed-contam-UP000005640.fas" \
  --reanalyse --rt-profiling \
  --var-mods 3 \
  --var-mod UniMod:35,15.994915,M --var-mod UniMod:1,42.010565,*n \
  --out "report.parquet" --matrices --qvalue 0.01 \
  --threads 32 --verbose 1 --peptidoforms
# 建库模板（无现成谱库时一次性生成；产物 human.predicted.speclib 供以后所有同物种实验的 --lib 复用）
# 漏切/修饰/窗口在此定格为谱库候选集；漏切官方推荐 1（某些样本类型 2 有益），改动后需重建库
/lustre/software/diann/2.6.1/diann261.sif /diann-2.6.1/diann-linux \
  --fasta "uniprot_human_reviewed.fas" \
  --fasta-search --predictor --gen-spec-lib --out-lib "human.predicted.speclib" \
  --var-mods 3 \
  --var-mod UniMod:35,15.994915,M --var-mod UniMod:1,42.010565,*n \
  --missed-cleavages 2 --met-excision \
  --min-pep-len 7 --max-pep-len 30 \
  --min-pr-mz 300 --max-pr-mz 1800 --min-pr-charge 1 --max-pr-charge 4 \
  --min-fr-mz 200 --max-fr-mz 1800 --cut K*,R* \
  --out "build.parquet" --threads 32 --verbose 1
模板与官方 README 对照（DIA-NN 2.6） ① 两阶段与参数分工：官方推荐“建库”与“分析”分开执行——预测谱库生成约每百万前体 2 分钟内完成，同物种实验一直复用。把两段合并成一条命令、同时写 --lib 与 --fasta-search --gen-spec-lib 并非官方用法。--fasta-search --predictor --gen-spec-lib --out-lib 只属于建库；--missed-cleavages --met-excision --min-pep-len --max-pep-len --min/max-pr-mz --min/max-pr-charge --min/max-fr-mz --cut 均只作用于 FASTA 酶切消化，纯库搜索时可省略（写了也会被忽略，不影响结果）。漏切数（--missed-cleavages）同理：官方默认推荐 1（“setting to 1 is optimal in most cases”），对某些样本类型设 2 可能有益，若 PTM 发生在决定酶切特异性的氨基酸上漏切需相应 +1。建库定几漏切，搜库结果里最多就是几——重搜想收紧只能在建库端改参数并重建库。 ② MBR 与 RT profiling：用预测谱库做定量分析时，官方建议始终开启 MBR（--reanalyse）——第一遍先用本次数据生成经验谱库、第二遍用它重搜，识别数与定量完整度更好；--rt-profiling 官方释义为“经验谱库按 IDs、RT 与 IM 轮廓生成”（官方对几乎所有流程的推荐设置），故二者常成对出现，组里实测也一直带着。反过来，若用的是 DIA-NN 自建的经验谱库（RT/IM 已来自实测数据），官方建议关掉 MBR。 ③ fasta 与 decoy 的角色：DIA-NN 的 FDR 对照的是它自己生成的 decoy（官方 README “Scoring”：对目标肽段做残基重排/单残基突变），用户不需要为 FDR 准备含 decoy 的 fasta；官方支持“自带 decoy”的唯一入口是在 .parquet 谱库中用 Flags 列标记（第三方建库软件接口，README “Custom decoys”），README 全文没有在 FASTA 中识别 decoy 条目的机制。加 fasta 的目的是让报告带上蛋白名/基因名并把修饰位点映射到蛋白序列（官方对 GUI “Add FASTA”的说明，纯注释用途）。注意：FragPipe 命名的 decoys-…-contam fasta 只做搜索注释没问题（本组实测通过，decoy 条目无对应肽段命中、不影响结果）；但据上述机制推断（非官方明文），拿它跑 --fasta-search 建库时其中的 decoy 条目会被当作普通蛋白一并消化进目标谱库，稳妥起见建库建议用不含 decoy 的 reviewed fasta。建库 FASTA 选择速查：① decoy——不要混入（DIA-NN 无 FASTA 识别机制，见上）；② contaminant（常见污染蛋白，如 FragPipe 的 contam 列表）——可并入，污染条目会被标注便于排除，对建库无害；③ isoforms——默认用 UniProt reviewed（canonical）即可，含 isoforms 会显著扩大搜索空间（建库/搜索更慢、RAM 更高），仅当需要区分剪接异构体时才加。 ④ 修饰声明：半胱氨酸 Carbamidomethyl（+57.021）是 DIA-NN 内置默认固定修饰，无需显式声明；只需用 --var-mod 声明可变修饰（本模板只声明 M 氧化＋蛋白 N 端乙酰化，官方提示其它修饰按需添加、宁少勿多），--var-mods 3 属官方认可范围（1–3）。素材旧命令中的 --unimod4/--unimod35 未被 2.6 官方命令行参考收录，属遗留写法，已删除。 ⑤ 细节：--cut K*,R* = 胰蛋白酶、不启用脯氨酸规则（K/R 后接 P 仍会切）；要经典胰蛋白酶（含 P 规则）写成 --cut K*,R*,!*P。--min-pr-charge 1 适用于 Orbitrap DIA；Bruker timsTOF（dia-PASEF）数据用预测库搜索时官方要求最小电荷为 2。原始素材命令存在缺“\”续行、-- var-mods 多空格等笔误，本模板已校正；行尾 \ 后不要留空格，否则整行会被截断成单条命令。
新手实操：新建 / 编辑 / 保存 / 退出作业脚本（vim 或 heredoc）

vim 三步建脚本：vim diann_job.sh 新建文件（文件名已存在则是打开编辑）→ 按 i 进入编辑模式（左下角出现 -- INSERT --），此时才能粘贴/输入内容 → 编辑完按 Esc 退出编辑模式 → 输入 :wq 回车，保存并退出（w=写入，q=退出）。

口诀：i 进、Esc 出、:wq 走。不保存直接强退用 :q!；提示 E37: No write since last change 表示有改动未保存，改用 :wq 或 :q!。

常见卡壳：① 还停留在编辑模式（-- INSERT -- 未消失）时输入 :wq 会被当成正文打进去——先按 Esc 再输入；② 冒号必须是英文半角 :，中文输入法下的全角 ： 无效；③ 终端误按 Ctrl+S 会冻结（Xshell/MobaXterm 同样），按 Ctrl+Q 恢复。

不想学 vim 的替代：heredoc 一次生成——粘贴完整脚本后另起一行输入 EOF 回车即写盘（'EOF' 加引号可防止变量提前展开）：

cat > diann_job.sh <<'EOF'
#!/bin/bash
#SBATCH --job-name=…（你的完整脚本粘贴于此）…
EOF

本机写好再上传（WinSCP/MobaXterm 等）：Windows 文本是 CRLF 换行，直接 sbatch 会让 #SBATCH 行尾带 \r 导致参数解析出错，上传后先执行 sed -i 's/\r$//' diann_job.sh 转成 LF。无论哪种方式，提交前先 bash -n diann_job.sh（无输出即语法正常），再 sbatch diann_job.sh。

3
提交与监控：sbatch diann_job.sh → squeue -l 确认状态 → tail -f 作业号.out 实时看进度（DIA-NN 会打印每步日志），或 ls -lg 看输出文件是否在增长。
4
完成与产物：作业显示 COMPLETED 后，在目录中检查输出（见 4.3）；结果即时拷回家目录/本地，勿长期堆放临时目录。sbatch 作业结束即自动停止计费，无需手动杀；若中途想停用 scancel JOBID。

4.3 输出文件说明与进度查看

文件含义
report.parquet主结果（谱图/肽段/蛋白定量矩阵），可用 Python 读取或 FragPipe 生态工具查看
report.stats.tsv / report.log.txt统计与日志：cat report.stats.tsv 查看运行统计（蛋白/肽段数等）
xxx.speclib（建库流程）生成的谱库，供后续批量定量复用
predicted.*（预测模式）预测谱库相关中间产物
*.quant（出现在 mzML 同目录）单样本识别＋定量的中间缓存：DIA-NN 先逐个文件独立处理、各自落盘 .quant，全部跑完再汇总做跨样本步骤。换谱库或改参数对同一批数据重新搜库前必须删除（rm -f *.quant），否则旧搜索的识别结果可能被复用；单次完整分析跑完无需理会它
作业号.out / .errSlurm 标准输出/错误（排查错误优先看 .err）
*.matrix.tsv 系列（开启 --matrices 后）按 --out 前缀派生的定量矩阵：report.pg_matrix.tsv（蛋白组）、report.pr_matrix.tsv（前体）、report.gg_matrix.tsv/report.unique_genes_matrix.tsv（基因/特异基因），另有 report.protein_description.tsv；均已按 1% FDR 过滤、可直接用于 Excel/R/Python

进度查看三件套：tail -f 作业号.out（实时，推荐）、grep "\[" 作业号.out（只显示带进度标记 [ 的行）、top -u 你的账号（确认进程在跑、CPU 占用是否合理）。命令不懂就看下方速记框。

查看类命令速记（Windows 视角） tail -f 文件＝盯着文件“尾部”，新内容自动追加显示（日志实时滚动；想停止查看按 Ctrl+C——只停查看，不影响作业）；grep "关键词" 文件＝只列出文件里含关键词的行（搜日志很方便）；cat 文件＝把整个文件内容打印到屏幕（适合小文件）；top＝Linux 版任务管理器（按 q 退出）；ls -l＝详细列出文件与大小。
主报告（.parquet）下游过滤建议（官方） 主报告设计为“先记录一切、由你过滤”：常用过滤为 run-specific Q.Value ≤ 0.01–0.05（DIA-NN 默认已按 5% 过滤写入）、Global.Q.Value ≤ 0.01（全局前体 1%）、Global.PG.Q.Value ≤ 0.01（全局蛋白组 1%）；*.matrix.tsv 已滤好可直接用。q-value 只用于筛选报告行，先过滤再做缺失值填充/统计。

4.4 DIA-NN 常见问题（团队亲历）

① 报错 Illegal instruction（作业提交后立即失败） 现象：.err 中出现 Illegal instruction 且行号指向 DIA-NN 命令行。排查顺序： 1) 检查作业目录文件是否齐全——fasta、谱库、所有 raw 是否真的都在并可读（团队曾因目录少拷贝几个文件，64 核上反复失败，补齐后 1 小时即跑完）； 2) 换 32 核 cu-1 队列再试：本组实测平台容器在部分 64 核（cpuPartition，Platinum 8358）节点出现指令集不兼容，32 核 cu-1（Gold 6242）稳定； 3) 核对命令是否缺 \ 续行、参数是否抄错。
② 日志长时间不更新 / report.out 不增长 先 top -u 账号 确认进程存活与 CPU%；若进程在但输出文件不动，多为程序仍在前期阶段（建库预测较慢）；若进程已消失，检查 .err 末尾。注意：只有 sbatch 作业才有“作业号.out”，salloc 交互式无此文件——交互式请把输出重定向到文件（> xxx.out 2>&1：>＝“把屏幕输出写入文件”，2>&1＝报错信息也一并写入，整段照抄即可）或直接看终端。平台手册页的旧命令常缺少重定向，导致报错信息刷屏并误以为 Xshell 崩溃。
③ 线程数（--threads）与核数怎么配 结论：32 核节点申请 64 核、跑 64 线程可以正常排队运行（组内实测；早期“32 核只能跑 32 线程”“64 线程不让跑/反而更慢”的说法不准确，已作废，本册 4.1 铁律③同此口径）。写法：#SBATCH --ntasks-per-node=64＋命令里 --threads 64，两处数字保持一致即可。但要认清：cu-1 为 32 物理核（超线程 64 逻辑核），超线程对 DIA-NN 这类计算密集流程通常没有额外加速——32 与 64 哪个更快以实测为准（同一节点各跑一小批数据对比耗时即可）。想提速优先拆多个作业并行（见《HPC 使用入门》3.4 团队经验③）。内存参考：官方估算约 0.5 GB/百万个库前体（可变修饰多、宏蛋白组会更高）；cu-1 单节点 192 GB 跑常规人/鼠预测库（百万级前体）绰绰有余，不必申请多节点。
